## Features

| ✅ | Feature |
|----|---------|
| ✅ | **Three distinct flavors** – `dev`, `staging`, `prod`. |

| ✅ | **Basic UI** (home screen, settings) to demonstrate app name & flavor. |
| ✅ | **Documentation** – this README + inline comments. |

## Getting Started

### Prerequisites

| Tool | Minimum version |
|------|-----------------|
| **Flutter SDK** | `3.19.0` (or newer) |
| **Dart SDK** | `3.3.0` |
| **Android Studio** / **IntelliJ** / **VS Code** | Any IDE with Flutter plugin |
| **Java** | JDK 11+ (for Android Gradle) |
| **Xcode** | 15.0+ (macOS only, for iOS) |
| **CocoaPods** | `1.12.0+` (iOS) |
| **Git** | any recent version |

> **Tip** – Run `flutter doctor -v` to verify your environment.

### Installation

1. **Clone the repository**

   ```bash
   git clone https://github.com/OmarSaeed20/flavorizr.git
   cd flavorizr
   ```

2. **Install Dart/Flutter dependencies**

   ```bash
   flutter pub get
   ```

3. **Generate the flavor files** (only needed the first time or when you edit `flavors/flavorizr.yaml`)

   ```bash
   flutter pub run flutter_flavorizr
   ```

   This command:
   - Creates Android product flavors (`dev`, `staging`, `prod`).
   - Generates iOS schemes & `.xcconfig` files.
   - Copies flavor‑specific icons, launch screens, and resources.
   - Updates `MainActivity.kt`, `AppDelegate.swift`, and `Info.plist`.

4. **(Optional) Install code‑generation packages**

   The project uses `injectable` for DI. Run:

   ```bash
   flutter pub run build_runner build --delete-conflicting-outputs
   ```

### Running the app

| Platform | Command | Description |
|----------|---------|-------------|
| Android (dev) | `flutter run --flavor dev -t lib/main_dev.dart` | Runs the **dev** flavor on a connected device/emulator. |
| Android (staging) | `flutter run --flavor staging -t lib/main_staging.dart` | Runs the **staging** flavor. |
| Android (prod) | `flutter run --flavor prod -t lib/main_prod.dart` | Runs the **prod** flavor. |
| iOS (dev) | `flutter run --flavor dev -t lib/main_dev.dart` | Same command works for iOS (requires a macOS host). |
| Web (any) | `flutter run -d chrome` | The web build uses the same Dart entry point (flavor is selected by compile‑time variable). |
| Desktop (any) | `flutter run -d windows` (or `macos`, `linux`) | Same principle; the flavors are baked into compiled code. |

> **NOTE** – The entry‑point files (`main_dev.dart`, `main_staging.dart`, `main_prod.dart`) are generated by `flavorizr`. They simply call `runApp(MyApp())` after initializing `FlavorConfig`.

## Flavor Configuration  

All flavor‑specific values are defined in two places:

1. **`flavors/flavorizr.yaml`** – Drives native resources (app IDs, icons, build types).  
2. **`lib/config/environment.dart`** – Holds Dart‑side constants such as API base URLs, Firebase config, feature‑toggles.

### Android

`android/app/build.gradle` will contain:

```gradle
flavorDimensions "app"

productFlavors {
    dev {
        dimension "app"
        applicationId "com.example.flavorizr.dev"
        resValue "string", "app_name", "Flavorizr Dev"
    }
    staging {
        dimension "app"
        applicationId "com.example.flavorizr.staging"
        resValue "string", "app_name", "Flavorizr Staging"
    }
    prod {
        dimension "app"
        applicationId "com.example.flavorizr"
        resValue "string", "app_name", "Flavorizr"
    }
}
```

Icons are placed under `android/app/src/<flavor>/res/mipmap-.../ic_launcher.png` and referenced automatically.

### iOS

`ios/Runner.xcworkspace` contains three schemes (`Dev`, `Staging`, `Prod`). Each scheme uses its own `.xcconfig` file:

```text
// ios/Configurations/Dev.xcconfig
PRODUCT_BUNDLE_IDENTIFIER = com.example.flavorizr.dev
APP_DISPLAY_NAME = Flavorizr Dev
```

Corresponding **App Icons** are stored in `ios/Runner/Assets.xcassets/<Flavor>.appiconset`.

### Dart / Flutter side

```dart
// lib/config/flavor_config.dart
enum Flavor { dev, staging, prod }

class FlavorConfig {
  final Flavor flavor;
  final String name;
  final String apiBaseUrl;

  const FlavorConfig._({
    required this.flavor,
    required this.name,
    required this.apiBaseUrl,
  });

  static late final FlavorConfig _instance;
  static FlavorConfig get instance => _instance;

  factory FlavorConfig({
    required Flavor flavor,
    required String name,
    required String apiBaseUrl,
  }) {
    _instance = FlavorConfig._(
      flavor: flavor,
      name: name,
      apiBaseUrl: apiBaseUrl,
    );
    return _instance;
  }
}
```

The generated `main_*.dart` files initialise this config automatically:

```dart
void main() {
  FlavorConfig(
    flavor: Flavor.dev,
    name: "Development",
    apiBaseUrl: "https://api.dev.example.com",
  );
  runApp(const MyApp());
}
```

You can access it anywhere:

```dart
final baseUrl = FlavorConfig.instance.apiBaseUrl;
```

## Building & Publishing  

### Android (APK / AAB)

```bash
# Dev (debug)
flutter build apk --flavor dev -t lib/main_dev.dart

# Staging (release)
flutter build appbundle --flavor staging -t lib/main_staging.dart

# Prod (release, Play Store)
flutter build appbundle --flavor prod -t lib/main_prod.dart
```

### iOS (IPA)

```bash
flutter build ios --release --flavor prod -t lib/main_prod.dart
# Then archive & upload via Xcode or Fastlane
```

### Web

```bash
flutter build web --profile   # For staging
flutter build web --release   # For prod
```

### Desktop

```bash
flutter build windows --release   # or macos / linux
```

## CI / CD (GitHub Actions)

`.github/workflows/flutter.yml` does:

1. **Setup** – Installs Flutter, caches deps.
2. **Lint** – `flutter analyze`.
3. **Test** – `flutter test --coverage`.
4. **Build** – Produces APK/AAB for each flavor *on push to `main`*.
5. **Upload Artifacts** – The built binaries are attached to the workflow run.

You can extend it with **Fastlane** for Play Store / App Store deployment.
